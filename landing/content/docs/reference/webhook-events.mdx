---
title: Webhook Events
description: Handle incoming messages and status updates from WhatsApp.
---

Better Zap processes WhatsApp webhook events and delivers them to your callbacks with parsed, normalized data.

## onMessage

Called when a user sends a message to your WhatsApp Business number.

```ts
const zap = betterZap({
  // ...config
  webhook: {
    onMessage: async (ctx) => {
      console.log(`From: ${ctx.phone}`);
      console.log(`Content: ${ctx.content}`);
      console.log(`Type: ${ctx.message.type}`);

      // Reply to the user
      await ctx.api.sendText(ctx.phone, "Thanks for your message!");

      // Mark as read
      await ctx.api.markAsRead(ctx.message.id);
    },
    onStatusUpdate: async () => {},
  },
});
```

### Message Context

| Property | Type | Description |
| --- | --- | --- |
| `message` | `IncomingMessage` | Raw WhatsApp message object |
| `content` | `string` | Human-readable content extracted from any message type |
| `phone` | `string` | Sender phone number (normalized 13-digit format) |
| `contact` | `object` | Sender contact info (`{ name, wa_id }`) |
| `db` | `BetterZapDatabase` | Your database instance |
| `api` | `WhatsAppService` | Service for sending messages |
| `logger` | `MessageLoggerService` | Message logging service |

When plugins are configured, their context is merged into `ctx` with full type inference.

### Supported Message Types

Better Zap extracts human-readable content from all WhatsApp message types. The built-in labels are in Brazilian Portuguese:

| Type | `ctx.content` |
| --- | --- |
| `text` | The text body, or `[texto vazio]` when empty |
| `image` | `[imagem]`, or `[imagem: <caption>]` |
| `audio` | `[áudio]` |
| `video` | `[vídeo]`, or `[vídeo: <caption>]` |
| `document` | `[documento: <filename>]`, or `[documento: arquivo]` without a filename |
| `location` | `[localização: <name>]`, or `[localização: <latitude>,<longitude>]` |
| `button` | `[botão: <text>]` |
| `interactive` | `[resposta botão: <title>]`, `[resposta lista: <title>]`, or `[interativo]` |
| `sticker` | `[figurinha]` |
| `reaction` | `[reação]` |
| `media_placeholder` | `[mídia]` |
| any other type | `[<type>]`, for example `[contacts]` |

### Custom labels

The labels above are Brazilian Portuguese by default. Set `webhook.resolveMessageContent` to replace them: its return value is stored as the message's `content` and passed to hooks as `ctx.content`, for incoming messages and for messages imported from coexistence history.

```ts
import { betterZap } from "@better-zap/hono";
import { getMessageContent } from "better-zap";

const zap = betterZap({
  // ...config
  webhook: {
    resolveMessageContent: (message) => {
      if (message.type === "image") return message.image?.caption ?? "[image]";
      if (message.type === "audio") return "[audio]";
      if (message.type === "sticker") return "[sticker]";
      return getMessageContent(message); // built-in label for everything else
    },
    onMessage: async (ctx) => {
      // ctx.content is what resolveMessageContent returned
    },
    onStatusUpdate: async () => {},
  },
});
```

## onStatusUpdate

Called when a message you sent changes status (sent, delivered, read, or failed).

```ts
webhook: {
  onStatusUpdate: async (ctx) => {
    console.log(`Message ${ctx.status.id} → ${ctx.status.status}`);
    // status.status is one of: "sent" | "delivered" | "read" | "failed"
  },
}
```

### Status Context

| Property | Type | Description |
| --- | --- | --- |
| `status` | `MessageStatus` | Status update object |
| `db` | `BetterZapDatabase` | Your database instance |
| `api` | `WhatsAppService` | Service for sending messages |
| `logger` | `MessageLoggerService` | Message logging service |

### Status Lifecycle

Statuses progress atomically — they can only advance forward:

```
sent → delivered → read
  └──────────────→ failed
```

The logger service enforces this: a message that's already `read` won't regress to `delivered`.

## Template events

Meta reviews a template after you create or edit it, and can later pause it, disable it, change its category or lower its quality score. Each change arrives as a webhook and is passed to one of four optional hooks:

| Hook | When it runs |
| --- | --- |
| `onTemplateStatusUpdate` | Meta approves, rejects, pauses, disables or otherwise changes a template's status (`message_template_status_update`) |
| `onTemplateQualityUpdate` | A template's quality score changes (`message_template_quality_update`) |
| `onTemplateCategoryUpdate` | Meta announces or applies a category change (`template_category_update`) |
| `onTemplateComponentsUpdate` | A template's content is edited (`message_template_components_update`) |

```ts
webhook: {
  onMessage: async () => {},
  onStatusUpdate: async () => {},
  onTemplateStatusUpdate: async (ctx) => {
    if (ctx.event === "APPROVED") {
      await markTemplateReady(ctx.wabaId, ctx.templateName, ctx.templateLanguage);
    }
    if (ctx.event === "REJECTED") {
      // ctx.reason is e.g. "INVALID_FORMAT"; Meta's details are in ctx.value.rejection_info
      await notifyRejection(ctx.templateName, ctx.reason, ctx.value.rejection_info);
    }
  },
}
```

Better Zap stores nothing for these events. If you keep a local copy of your templates, update it in the hook.

### Template Context

Every template hook receives:

| Property | Type | Description |
| --- | --- | --- |
| `wabaId` | `string` | The business account that owns the template (the webhook entry id) |
| `templateId` | `string` | Template id |
| `templateName` | `string` | Template name |
| `templateLanguage` | `string` | Language code with `-` replaced by `_`, e.g. `en_US`. Empty when Meta sends none |
| `value` | `object` | The payload exactly as Meta sent it |
| `change` | `WebhookChange` | The raw webhook change |

Through `betterZap()`, the context also has `db`, `api`, `logger` and your plugins' context. Each hook adds:

| Hook | Properties |
| --- | --- |
| `onTemplateStatusUpdate` | `event` (`APPROVED`, `REJECTED`, `PAUSED`, `DISABLED`, ...), `reason` (`null` when Meta sends none or `NONE`), `category` |
| `onTemplateQualityUpdate` | `previousQualityScore`, `newQualityScore` (`GREEN`, `YELLOW`, `RED` or `UNKNOWN`; a missing score is `UNKNOWN`) |
| `onTemplateCategoryUpdate` | `phase` (`"scheduled"` or `"changed"`), `currentCategory`, `previousCategory` (when changed), `nextCategory` and `scheduledFor` (when scheduled) |
| `onTemplateComponentsUpdate` | `body`, `header`, `footer`, `buttons` (`{ type, text?, url?, phoneNumber? }[]`) |

### Notes

- Subscribe your app to the four webhook fields above in Meta's App Dashboard. The access token needs the `whatsapp_business_management` permission.
- These webhooks belong to a business account, not a phone number. Use `ctx.wabaId`; there is no phone number id.
- In an announced category change, `currentCategory` is the template's category today and `nextCategory` is the one Meta will apply at `scheduledFor`.
- `templateId` is a string, but Meta sends it as a JSON number. For very large ids, prefer matching on `templateName` plus `templateLanguage`.
- A template webhook without a template id or name is logged as `webhook.template_event_invalid` and skipped. A hook that throws is logged and does not stop the rest of the webhook.

The readers behind these hooks (`readTemplateStatusUpdate`, `readTemplateQualityUpdate`, `readTemplateCategoryUpdate`, `readTemplateComponentsUpdate`) are exported from `better-zap` for apps that handle raw payloads themselves.

## Processing Model

Better Zap's webhook is designed for reliability:

1. **Signature verification** — Every `POST /webhook` is validated with HMAC-SHA256 using your `appSecret`
2. **Deduplication** — Messages are checked against the log store before processing
3. **Instant response** — Meta receives `200 OK` immediately
4. **Async processing** — Your callbacks run in `executionCtx.waitUntil()`, so they don't block the response
5. **Plugin hooks first** — Plugin `onMessage`/`onStatusUpdate` hooks run before your callbacks
6. **Automatic logging** — Incoming messages are logged before your callback runs

## Error Handling

If your `onMessage` or `onStatusUpdate` callback throws, the error is caught and logged. Meta still receives `200 OK` (to prevent retry loops).

For custom error handling, wrap your callback logic in try/catch:

```ts
onMessage: async (ctx) => {
  try {
    await processMessage(ctx);
  } catch (err) {
    await notifyErrorTracking(err, ctx);
  }
},
```
