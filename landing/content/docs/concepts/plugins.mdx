title: Plugins

Plugins let you extend Better Zap's functionality by injecting context, services, and hooks into the message processing pipeline.

## Creating a Plugin

A plugin is an object with an `id`, an optional `init` function, and optional hooks. A plugin can hook any webhook event, not only messages and statuses (see [Plugin Lifecycle](#plugin-lifecycle)):

```ts
import type { BetterZapPlugin, BetterZapDatabase } from "better-zap";

const analyticsPlugin: BetterZapPlugin<
  BetterZapDatabase,
  { analytics: AnalyticsService },  // Context to inject
  { analytics: AnalyticsService }   // Services to expose
> = {
  id: "analytics",

  init: (ctx) => {
    const analytics = new AnalyticsService(ctx.config);

    return {
      context: { analytics },
      services: { analytics },
    };
  },

  hooks: {
    onMessage: async (ctx) => {
      await ctx.analytics.trackMessage(ctx.phone, ctx.content);
    },
    onStatusUpdate: async (ctx) => {
      await ctx.analytics.trackStatus(ctx.status);
    },
  },
};
```

## Using Plugins

Pass plugins to `betterZap()`:

```ts
const zap = betterZap({
  // ...config
  plugins: [analyticsPlugin, queuePlugin],
  webhook: {
    onMessage: async (ctx) => {
      // Plugin context is merged and type-safe
      await ctx.analytics.trackCustomEvent("webhook_received");
    },
    onStatusUpdate: async () => {},
  },
});

// Plugin services are accessible
zap.services.analytics.getReport();
```

## Plugin Lifecycle

**`init()`** runs once, synchronously, when `betterZap()` is called. Plugins are initialized in array order. `init` receives the database, config, core context and core services, plus the context and services of the plugins before it, and returns more context and services to merge.

**Hooks** run for each webhook event, **before** your own `webhook` hook for the same event. They receive the event context merged with the Better Zap context (`db`, `api`, `logger`) and every plugin's context. A plugin can define any of these:

| Hook | When it runs |
| --- | --- |
| `onMessage` | Once per incoming message, after SDK pre-processing |
| `onStatusUpdate` | Once per delivery status update (sent → delivered → read → failed) |
| `onCoexistenceHistory` | Once per history webhook, after SDK pre-processing |
| `onSmbAppStateSync` | Once per SMB app state sync webhook, after SDK pre-processing |
| `onSmbMessageEcho` | Once per app message echo webhook, after SDK pre-processing |
| `onCoexistenceAccountUpdate` | Once per coexistence account lifecycle webhook |
| `onCoexistenceAccountOffboarded` | Once per coexistence offboarding lifecycle webhook |
| `onCoexistenceAccountReconnected` | Once per coexistence background reconnection lifecycle webhook |
| `onCoexistenceMessageEdit` | For coexistence message edit webhooks |
| `onCoexistenceMessageRevoke` | For coexistence message revoke webhooks |
| `onCoexistenceUnsupportedMessage` | When a coexistence webhook contains unsupported or error content |
| `onTemplateStatusUpdate` | When Meta approves, rejects, pauses, disables or otherwise changes a template's status |
| `onTemplateQualityUpdate` | When a template's quality score changes |
| `onTemplateCategoryUpdate` | When Meta announces or applies a template category change |
| `onTemplateComponentsUpdate` | When a template's content is edited |

## Rules

- Plugin ids must be unique.
- `init` must be synchronous. If a plugin needs asynchronous setup, create the client lazily inside a service.
- A plugin cannot return the context keys `db`, `api` or `logger`, the service keys `whatsapp` or `logger`, or a key another plugin already returned. `betterZap()` throws at startup if it does, and the error names the plugin.
- For each event, plugin hooks run in array order, before your own hook.
- A plugin hook that throws is logged as `plugin.<event>_failed` (for example `plugin.on_coexistence_message_edit_failed`) and does not stop the other plugins or your hook.
- `onMessage` and `onStatusUpdate` run after Better Zap has stored the message or applied the status, so they observe it and cannot cancel it. A repeated delivery of the same message, or a status that does not move the message forward, runs neither hook.
- The coexistence hooks run on every delivery. The history and message echo contexts report how many messages were new and how many were duplicates.

## Type Inference

The generic parameters on `BetterZapPlugin` enable full type inference:

```ts
BetterZapPlugin<
  TDatabase,   // Your database type
  TContext,     // What this plugin adds to the hook context
  TServices,   // What this plugin adds to the services object
>
```

When multiple plugins are used, their contexts and services are intersected:

```ts
// If pluginA adds { queue: QueueService }
// and pluginB adds { analytics: AnalyticsService }
// then ctx in onMessage has both: ctx.queue and ctx.analytics
```

## Init Context

The `init` function receives:

| Property | Type | Description |
| --- | --- | --- |
| `database` | `TDatabase` | Your database instance |
| `config` | `BetterZapCoreConfig` | WhatsApp API config (token, phoneId, etc.) |
| `context` | `BetterZapContext` | Core context + context from earlier plugins |
| `services` | `BetterZapServices` | Core services + services from earlier plugins |
| `log` | `Logger` | Logger instance |

## Example: Queue Plugin

```ts
const queuePlugin: BetterZapPlugin<
  MyDatabase,
  { queuePosition: (phone: string) => Promise<number> },
  { queue: QueueManager }
> = {
  id: "queue",

  init: ({ database, log }) => {
    const queue = new QueueManager(database, log);

    return {
      context: {
        queuePosition: (phone: string) => queue.getPosition(phone),
      },
      services: { queue },
    };
  },

  hooks: {
    onMessage: async (ctx) => {
      if (ctx.content === "fila" || ctx.content === "queue") {
        const position = await ctx.queuePosition(ctx.phone);
        await ctx.api.sendText(ctx.phone, `You are #${position} in the queue.`);
      }
    },
  },
};
```
